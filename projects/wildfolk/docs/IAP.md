# Store · Google Play consumable Gem

Foundation4 implements the purchase foundation, **not live sales activation**. `StoreSettings.json`, `backend/src/iap-config.json` and the proposed catalog ship OFF/unregistered. Alpha never initializes or launches real billing; Development uses explicitly isolated fixtures only. Production deployment/activation, actual Google transactions and device tests remain release gates. [Research and evidence](../validation/store-iap/REVIEW.md).

## Authority and recovery

`IStoreBillingClient` separates UI from the native Java Billing9.1.0 bridge. No Unity IAP package or second wallet is introduced. Native SDK returns metadata/purchase tokens/owned purchases; it never grants Gem or consumes. Its Java callback enters a main-thread C# queue, reconnect/resume queries owned purchases, and disconnection clears stale prices.

1. Require connected, Google Play Games linked UGS identity; reject anonymous/offline/conflict/deletion and wrong environment. Server re-queries Authentication and protected account, not the client's Linked bool. Production and all external-review gates must be explicit; new starts also require the existing economy enabled policy and a valid Play Integrity build proof. Integrity is not payment proof.
2. `LowfirePurchase.BeginPurchase` freezes product/amount/revision/account/profile binding. Account hash includes project/environment/PlayerId; profile hash includes that account and server authorization. The same immutable product authorization may cover repeated independently paid tokens. OperationId retries are not financial identity.
3. Google flow carries both obfuscated IDs. Pending grants nothing. Scope-bound atomic/checksummed client journal persists unfulfilled tokens and stable operation IDs, max64. It is an outbox, not trusted payment proof or balance.
4. `LowfirePlayVerify` queries actual Google Developer API `purchases.productsv2` using a server-only service account secret. Require expected package, exact product/quantity1, PURCHASED, account/profile binding, supported consumption state and TEST when TestOnly. Client amount/price/verified fields have no authority. Unknown already-consumed purchases cannot mint Gem.
5. Durable protected pending hash → global Private token-hash owner binding under account-creation/deletion gate → Private Prepared receipt → existing Economy2 CAS grants `iap_purchase` and permanent `iap:google_play:<hash>` source. Archived sources retain deduplication; no generic public grant endpoint.
6. Private Granted receipt survives response loss. A separate bounded invocation queries Google and consumes **after** durable grant; consumption acknowledges this consumable. No separate premature client acknowledgement. Complete removes server raw token and pending entry. A crash after Google consume re-queries consumption state and completes without re-grant.
7. Store open/resume/manual recovery queries owned purchases and retries up to4 local entries, up to3 bounded server recovery calls (one Google stage per invocation). Server pending records recover even after reinstall without the local queue. Consumed Gem is never restored as a fresh purchase. Account switches retain late tokens only in their original account journal; deletion clears that scope, including a prior-session queue before reopening Store.

`PurchaseEnabled` stops new sales; reviewed `SettlementEnabled` is independent so earned purchases can finish. Do not disable settlement during incident response without reviewing pending records. Recovery requires linked identity and scope validation. No per-frame network polling. Automatic background monitoring is not deployed; release operations must recover/alert before Google's acknowledgement deadline. Reinstall/device change tests currently model backend state and isolated service restart; actual Google/device proof remains outstanding.

## Financial records and reversal

IAP metadata/journal/receipt Schema1 are separate from Save14/Profile2/CloudProfile1/Economy2/Protocol23/generation3, all unchanged. Private Prepared/Granted receipts temporarily hold raw token for consume retry, product, amount, bindings, Google order reference and phases. Completed/Reversed removes the raw token. Never put raw token/order ID/credentials in public UI, logs, feedback or ledger. Safe history exposes transaction reference/product/amount/phase/times/reclaimed/shortfall. Ledger holds only token hash; pending client files are account/environment bound, not encrypted and not a hardware secure store.

Verified Google cancellation/Voided entry alone triggers reversal. `iap_refund:google_play:<hash>` is permanent, including a verified zero-delta marker when already spent/not granted. Reclaim min(current balance, original grant), record shortfall, keep wallet ≥0. Shortfall blocks new paid starts pending case review; no automatic ban, Engineer revocation, future free-Gem confiscation or negative debt. Gem is fungible, so reclamation is from available balance rather than tracking individual paid/free units. Partial-quantity refunds are outside the quantity1 catalog.

Hosted RTDN/PubSub is deferred; no public unverified notification-to-grant route exists. `iap-admin.cjs voided` queries actual Google feed with overlapping30-day lookback, paginates up to4pages/run and retains an external cursor. Re-run until Complete, monitor at least daily. Refund without revoke may be absent from the feed: operator must inspect Console and explicitly reconcile a revocation/case; do not invent a client refund proof. Continuous pending monitor, alert destination/on-call and a tested Google refund procedure are activation blockers.

`backend/tools/iap-admin.cjs` uses existing scoped AdminApi credentials, not player credentials:

```text
node backend/tools/iap-admin.cjs lookup --project <project> --environment <environment-id> --support <support-id>
node backend/tools/iap-admin.cjs recover --project <project> --environment <environment-id> --player <player-id> --operator <operator> --case <ticket>
node backend/tools/iap-admin.cjs recover --project <project> --environment <environment-id> --player <player-id> --operator <operator> --case <ticket> --apply --confirm RECONCILE_PURCHASES
node backend/tools/iap-admin.cjs voided --project <project> --environment <environment-id> --operator <operator> --case <ticket> --journal <absolute-path-outside-repository>
```

Voided apply additionally needs `--apply --confirm RECONCILE_PURCHASES`. `resolve-review` records operator/case disposition, grants nothing, defaults dry-run. `LOWFIRE_GOOGLE_PLAY_CREDENTIALS_FILE` is an operator-local secret file path; never commit its contents. Support lookup pages the existing archived ledger and safe receipt references; duplicates/validation/consume/refund states are visible without exposing raw tokens.

Deletion marks the account before financial cleanup, preventing races. Financial accounts require an owner-reviewed policy reference and ReviewAt before disabling Authentication. Private purchase details are deleted; global dedup receipt becomes minimal DeletedOwner/hash/product/source/policy/review tombstone without PlayerId/token/order. An attempted replay cannot bind a different owner. Other archive/source/player data follow existing resumable deletion order. Retention duration/legal basis and review/purge execution must be decided by the owner; **no statutory period is guessed**. See [operations](BACKEND_OPERATIONS.md).

## External activation procedure — SETUP_REQUIRED

No real Play product, API credential, merchant, public Privacy/Deletion URL or Google test transaction was created in this pass. Use real values only; no credential through chat/Git.

1. Play Console: finish developer/merchant payments profile and app `com.gltam.lowfire`; confirm package/signing ownership and countries. Complete existing PGS/OAuth/Integrity setup from SETUP_REQUIRED. Do not change package to bypass registration.
2. Play Console → **Monetize with Play → Products → One-time products**: register reviewed proposed IDs, one ordinary buy purchase option each, region availability/local prices and descriptions. Record actual IDs/status/prices in owner setup evidence. No fake registration; no bulk auto-activation.
3. Confirm quantity1 consumable behavior. No rental/preorder/offer. Review24/72/144 against actual localized tiers and existing120/8 costs. Update Proposed=false only after cross-check; sync server catalog and revalidate immutable published amounts.
4. Google Cloud Console: enable Google Play Android Developer API for the chosen project and create least-privilege service account. Play Console → **Users and permissions**: invite that service account, restrict to Lowfire, grant permissions necessary to view orders/subscriptions and manage orders/consumption/refunds. Developer API no longer requires linking the developer account to a Cloud project. Validate real access using controlled purchases, never broad admin as a workaround. [Official API setup](https://developers.google.com/android-publisher/getting_started).
5. Owner stores service-account JSON directly in UGS Dashboard → Secret Manager, exact secret `LOWFIRE_GOOGLE_PLAY_SERVICE_ACCOUNT`, scoped to the intended environment/scripts. No secret in Resources, source, screenshot, fixture, Git or chat. Operator local file only for reviewed reconciliation. Test missing/rotated/revoked credentials fail closed.
6. Play Console → **Settings → License testing**: register actual test Google accounts/test response instruments; distribute through a controlled internal test release with correct signing/application ID and accepted tester link. **A test track alone does not prevent real charges.** [License setup](https://support.google.com/googleplay/android-developer/answer/6062777), [Billing tests](https://developer.android.com/google/play/billing/test).
7. Alpha remains hard OFF, including license purchases. Future real Billing QA requires a separately reviewed controlled Production-config test artifact, all preconditions and registered license tester/test card. Server TestOnly=true rejects non-TEST proof **after payment**; it cannot prove before payment that a user is a license tester. Do not enable public Production in order to test. This pass performs neither activation nor a real Google purchase.
8. Deploy/review all seven server bundles, existing Access Control/private data policy and Google verifier in the intended environment. Existing setup stays OFF for Development/Alpha. For future Production, provision approved config with `iap-setup` dry-run and reviewed explicit ENABLE_PRODUCTION_PURCHASES confirmation; preserve other policy fields/writeLock. Settlement activation needs ExternalSetupReviewed and a real FinancialRetentionPolicy reference. Do not stop settlement merely to stop new sales.
9. Set up a pending recovery monitor/alert and daily Voided scan with durable external cursor, service permissions,30-day catch-up and incident runbook. Confirm full pagination and Google revoke/refund behavior; configure RTDN only as a separately approved resource task. No currently running scheduler/receiver is implied.
10. Publish actual Privacy Policy and external Account Deletion URL in app/backend configuration and Console; specify financial purposes/recipients/security/retention/deletion exceptions and contact. Review Google **Data safety purchase history/financial information, identifiers and third parties**, and SDK collection. Google processes payment; Lowfire does not collect payment card details. Decide audience/children/Families requirements before activation. [Data safety](https://support.google.com/googleplay/android-developer/answer/10787469), [deletion](https://support.google.com/googleplay/android-developer/answer/13327111), [Families](https://support.google.com/googleplay/android-developer/answer/9893335). These are setup checks, not a legal compliance certification.
11. On actual Android license test device validate regional ProductDetails, buy/cancel/pending/deferred→paid, kill before/after grant/consume, offline/reconnect, second device/reinstall, repeated same SKU, linked-account switch, duplicate callbacks, refund/revoke, deletion, native resume and real Google errors. Reconcile Console/Google/receipt/Economy ledger; no fixture acceptance as financial proof.

Only after owner approval and all release blockers resolved, enable reviewed client Production flags/catalog/backend, verified build/PGS/Integrity/policy and live mode (TestOnly=false intentionally). Re-check least privilege, alerts, refund/support readiness, Google policy and privacy. Production remains OFF at Foundation4 completion. ## Economy and limits

No free rewards/costs changed: start0, achievements lifetime213, newcomer45, monthly40, rewarded1/day, Engineer120, SP revive8. [Model](../validation/store-iap/economy-model.json) is an illustrative30/90-day budget, not telemetry or time-to-earn proof. Ads/buying are optional; newcomer45+two monthly40 totals125 without either. Engineer utility/repair/turret and overclock/overrepair create gameplay impact, and revival accelerates attempts. Cash acceleration is a real advantage; no claim of zero pay-to-win. Ordinary multiplayer combat balance is not sold directly. Engineer unlock is one-off, leaving revive as a weak repeating sink; maximum144 is deliberately small. Large repeated purchases can accumulate with no useful demand, so do not expand catalog/promotions or invent sinks in this pass.
