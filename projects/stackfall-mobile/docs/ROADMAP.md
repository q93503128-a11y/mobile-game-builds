# Stackfall Mobile 개발 로드맵

현재 단계: `Phase 1 source implementation complete → Unity validation gate`

엔진: `Unity 6.3 LTS / C#`

원칙: 콘텐츠를 많이 만드는 것보다 먼저 코어 전투와 데이터 구조가 맞는지 검증한다. 임시 구현을 쌓은 뒤 나중에 갈아엎는 방식은 피한다. 매 작업마다 Unity Editor를 실행하지는 않되, Unity 직렬화·에셋·플랫폼 의존 변경은 정해진 검증 게이트를 통과하기 전 최종 완료로 판정하지 않는다. 세부 규칙은 `ENGINE_WORKFLOW.md`를 따른다.

## Phase 0 — 정본/연구 고정 ✅

완료:
- 기존 웹 Stackfall 기능 목록 전수 분류
- 경쟁작 수치/경제/콘텐츠 벤치마크
- Design Bible 정합성 점검
- 모바일 플랫폼 요구사항 정리
- Unity 6.3 LTS 프로젝트 구조/검증 정책 고정
- 부품 6슬롯/첫 S 24부품/가챠/경제 V0
- 12개 공격 6단 진화
- 초기 8챕터/적/엘리트/보스 카탈로그
- 홈/격납고 UI 정보구조
- 던전/보스랭킹/무한탑/아레나/길드보스 구조
- 길드/글로벌·국가 채팅/모더레이션
- 초기 정적/계정/전투 데이터 스키마
- Unity 전 정적 데이터 검증기

Phase 0에서 만든 수치는 출시 확정값이 아니라 Phase 1~4 실플레이/경제 검증을 위한 V0 기준이다.

## Phase 1 — 전투 프로토타입 🧪 Unity 검증 대기

소스 구현 완료:
- 모바일 드래그 이동 + PC 확인용 키보드 이동
- 자동 조준 대상 레지스트리
- 풀링 기반 적/경험치 오브/투사체/중력장
- 시간에 따라 증가하는 일반 적 압력
- 90/180/240초 엘리트
- 300초 최종 보스
- 엘리트 예고 돌진 패턴
- 보스 거리 유지 + 광역 펄스 예고 + 돌진 교대 패턴
- 경험치/레벨업
- 실제 3택 강화 선택
- 코어 펄스: 자동 추적/집중 투사체
- 펄스 블레이드: 공전/근접 지속타격
- 중력 우물: 설치/집속/범위 피해
- 선체/동력/보스 타이머/보스 체력 HUD
- 클리어/실패 상태
- 보스전 잡몹 압력 별도 제한
- 위험 범위 시각표현과 실제 판정 반경 정합
- Runtime source hygiene 검사 + GitHub Actions 정적 검사

이 3개 공격은 서로 구현 방식이 달라 전투 프레임워크의 확장성을 검증하기 좋다.

Unity에서 반드시 검증할 항목:
- [ ] Editor import/compile 오류 0
- [ ] 빈 씬 Play 진입 시 런타임 자동 생성
- [ ] 세로 화면에서 한 손 이동이 자연스러움
- [ ] 자동 조준이 답답하지 않음
- [ ] 레벨업 3택이 정상적으로 전투를 멈추고 복귀함
- [ ] 세 공격의 역할과 시각이 구분됨
- [ ] 엘리트 돌진 예고를 보고 피할 수 있음
- [ ] 보스 펄스의 보이는 범위와 실제 피격 범위가 일치함
- [ ] 5분 보스까지 난이도/성장 속도가 납득 가능함
- [ ] 5분 이상 플레이에서 프레임/메모리 악화가 누적되지 않음
- [ ] Console error 0
- [ ] Android 테스트 빌드 최소 1회

### 사용자 테스트 요청 시점

현재가 첫 사용자 Unity 테스트 게이트다. 소스/정적 검사는 통과했지만 Unity Editor import/compile/실플레이는 사용자 환경에서 실제 확인해야 Phase 1 완료로 판정한다.

이 단계에서는 상점/가챠/길드 UI를 먼저 만들지 않는다.

## Phase 2 — 데이터 주도 콘텐츠 구조

목표:
- 적/웨이브/스테이지/부품/스킬을 코드 하드코딩 대신 데이터로 정의
- 데이터 스키마
- ID 중복/누락 참조/수치 범위 검사
- 밸런스 시뮬레이션 도구 기반

Phase 0에서 데이터 스키마와 기본 검증기는 선행 완료했다. Phase 2에서는 이를 실제 Unity 런타임 데이터 로더와 콘텐츠 생산 파이프라인으로 연결한다.

완료 조건:
- 새 스테이지를 핵심 코드 수정 없이 추가 가능
- 새 부품을 데이터+필요한 고유 동작 모듈로 추가 가능
- 경제 숫자를 한 정본에서 관리
- Unity에서 데이터 import/참조가 깨지지 않음

## Phase 3 — 영구 부품 시스템

목표:
- 코어/프레임/드라이브/임팩터/오비터/리액터
- 장착/교체
- 슬롯 레벨
- 등급
- 합성/돌파
- 세트 효과
- 외형 변형
- 프리셋

검증:
- 새 부품 획득 시 기존 기본 강화 투자가 유지됨
- 중복 부품 가치가 명확함
- 6세트만 정답이 되지 않음
- 외형 변화가 실제 전투 가독성을 해치지 않음

Unity 게이트:
- 장착/해제 시 Prefab/참조 오류 없음
- 부품 외형 변형이 실제 인게임에 반영됨
- 저장/불러오기 후 동일 기체 복원
- Android 화면에서 외형/이펙트 가독성 확인

## Phase 4 — 메인 진행/경제

목표:
- 메인 스테이지 진행도
- 기본 재화
- 보상 테이블
- 일일/주간 공급량
- 에너지 사용 여부 확정
- 무료 유저 성장곡선
- 소과금/중과금/고과금 모델 비교

필수 산출:
- 30/90/180일 경제 시뮬레이션 재검증
- S 부품 기대 획득 기간 실측 보정
- 6슬롯 성장 기간
- 재화 source/sink 표

## Phase 5 — 가챠/상점/수익화

목표:
- 일반 소환
- S 프로토타입 픽업
- 천장
- 배너 이월
- 패키지
- 성장 기금
- 월정액
- 시즌 패스
- 보상형 광고
- 광고 제거

검증:
- 확률 합 100%
- 천장 경계 테스트
- 중복 결제/중복 수령 방지
- 잘못된 가격/상품 ID fail-closed
- 서버가 결과를 결정

Unity/모바일 게이트:
- 실제 Android 테스트 상품/광고 연동 검증
- 결제 성공/취소/실패/복구 흐름 확인
- 앱 중단/복귀 후 중복 지급 없음

## Phase 11 — 콘텐츠 생산

출시 후보 규모는 프로토타입 결과로 확정한다.

초기 가설:

- 충분한 메인 스테이지
- 6부품 슬롯
- 복수 일반 부품군

- 보스/엘리트 변형
- 던전/탑/아레나/길드

스테이지 수를 채우기 위해 수동 복붙하지 않는다. 웨이브/적 조합/환경 규칙을 데이터화해 제작 효율을 높인다.

## Unity 검증 주기

모든 소규모 작업마다 Unity를 열지 않는다.

기본 주기:
1. GitHub 정본에서 기능 묶음 개발
2. 코드/데이터/문서 자체 검증
3. Unity 의존 변경은 `검증 대기`로 표시
4. 기능 묶음 또는 마일스톤 종료 시 Unity Editor import/compile/Play Mode 검증
5. 주요 전투/플랫폼 단계에서는 Android 빌드 검증
6. 발견된 오류는 다음 기능으로 넘기지 않고 현재 묶음에서 정리

## 작업 순서 금지사항

다음 순서를 금지한다.

- 코어 전투 검증 전 대량 스테이지 제작
- 경제 시뮬레이션 전 상품 가격 대량 확정
- 서버 권위 설계 전 클라이언트 가챠 구현
- 길드 기본 기능 전 길드전 구현
- 프로파일링 전 대량 VFX 콘텐츠 추가
- 구 구현 삭제 없이 새 구현 병렬 누적
- Unity 검증이 필요한 변경을 장기간 누적하면서 완료 처리
