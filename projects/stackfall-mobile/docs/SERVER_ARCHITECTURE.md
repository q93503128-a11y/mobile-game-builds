# Stackfall Mobile 서버 아키텍처 원칙

상태: 초기 설계. 기술 스택은 아직 확정하지 않는다.

## 1. 핵심 원칙

라이브서비스 가치가 있는 상태는 클라이언트를 신뢰하지 않는다.

서버 정본 대상:

- 계정
- 프리미엄/일반 재화
- 인벤토리
- 부품 레벨/등급/돌파
- 가챠 결과와 천장
- 상품 구매/수령
- 메인 진행도
- 던전/아레나/보스 입장 횟수
- 랭킹 기록
- 길드
- 채팅 권한/제재
- 이벤트 진행도
- 시즌 보상

## 2. 전투 처리

초기 목표는 모든 전투 프레임을 서버에서 실시간 시뮬레이션하는 것이 아니다.

권장 흐름:

1. 클라이언트가 스테이지 입장 요청
2. 서버가 현재 부품/진행도/입장재화를 검증
3. 서버가 battle session ID, 규칙 버전, 필요 시 seed/nonce를 발급
4. 클라이언트가 로컬에서 전투 실행
5. 종료 시 결과/요약 telemetry 제출
6. 서버가 시간, 진행도, 허용 범위, session 재사용, 비정상 수치 등을 검증
7. 서버가 보상을 최종 확정하고 한 번만 지급

경쟁 점수일수록 검증 강도를 높인다.

## 3. 경제 요청

모든 경제 mutation은 중복 요청에 안전해야 한다.

예:
- 가챠
- 상품 수령
- 강화
- 합성
- 보상 수령

요청별 idempotency key 또는 동등한 중복 방지 장치를 둔다.

## 4. 가챠

- RNG는 서버에서 결정
- 배너 ID/버전 명시
- 천장 상태 서버 저장
- 결과와 천장 변화는 하나의 원자적 처리로 묶음
- 결제/재화 차감 성공 없이 아이템만 지급되는 상태 금지
- 재시도 시 동일 요청이 두 번 뽑히지 않게 함

## 5. 랭킹

랭킹 제출값을 그대로 신뢰하지 않는다.

최소 검증 후보:

- 해당 콘텐츠 입장 세션 존재
- 시작/종료 시간
- 보유 전투력/부품 스냅샷
- 허용 가능한 피해량/진행도 범위
- 클라이언트 버전
- 규칙/밸런스 버전
- 동일 세션 중복 제출

상위 이상치 기록은 추가 감사 대상으로 분리할 수 있다.

## 6. 길드

동시성 문제가 많은 기능이므로 서버 트랜잭션 경계를 명확히 한다.

예:
- 가입 정원 경쟁
- 길드 기부
- 길드 보스 누적 피해
- 길드 상점 구매
- 길드전 보상

클라이언트 캐시만 보고 길드 정원을 확정하지 않는다.

## 7. 채팅

채널:
- global
- country
- guild

필수:
- 서버 rate limit
- 메시지 길이 제한
- 신고
- 차단
- 금칙어/스팸 필터
- 제재 상태
- 메시지 ID/시간

글로벌 채팅은 샤딩/채널 분산이 필요할 수 있다.

## 8. 데이터 버전

저장 데이터와 라이브 밸런스 데이터에 버전을 둔다.

전투 세션은 시작 당시 규칙 버전을 기록해, 전투 중 밸런스가 갱신되더라도 결과 검증이 흔들리지 않게 한다.

## 9. 운영 설정

원격으로 바꿀 수 있는 후보:

- 이벤트 기간
- 배너 기간
- 상품 노출
- 보상 배율
- 일부 난이도 계수
- 기능 플래그

금지:
- 검증 없는 임의 JSON을 즉시 전체 유저에게 적용
- 서버/클라이언트 스키마가 다른 상태에서 강제 활성화

## 10. 로그와 감사

최소 감사 로그 후보:

- 결제 검증
- 가챠
- 고가치 재화 증감
- 희귀 부품 획득/분해
- 랭킹 상위 기록 제출
- 길드 권한 변경
- 운영자 보상

개인정보는 필요한 최소 범위만 기록한다.

## 11. 아직 미확정

- 백엔드 언어/프레임워크
- DB
- 실시간 채팅 인프라
- 인증 공급자
- 클라우드
- 국가 판정 정책
- 샤드 전략
- 전투 결과 검증 깊이

기술 선택은 예상 동시접속, 월 운영비, 개발 난이도, 모바일 SDK 지원을 비교한 뒤 결정한다.
